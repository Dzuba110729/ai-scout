# AI-Скаут — внутренний монитор конкурентов

## Что делаем

Внутренний инструмент (не паблик SaaS) для команды и себя лично, вдохновлённый сервисом
[AI-Скаут от Click.ru](https://partners.click.ru/promo_scout). Отслеживает сайты конкурентов
и с помощью ИИ фиксирует:

- **новые страницы** конкурента (лендинги, офферы) — в день публикации;
- **изменения контента** (цены, тексты, УТП, CTA) — с датировкой;
- **удаление страниц** — как сигнал смены стратегии конкурента.

Старт: **1 конкурент**, обход **раз в неделю**. Архитектура должна расширяться до
нескольких конкурентов без переписывания с нуля, но переусложнять сейчас не нужно.

## Ключевые ограничения (важно, определяют архитектуру)

- **ИИ-анализ только через подписку Claude Code CLI** (`claude -p`, headless-режим).
  НЕ используем платный Anthropic API — принят риск, что личная подписка не рассчитана
  на автоматизированные вызовы, но при частоте раз в неделю на 1 сайт нагрузка минимальна.
- **Антибот-защита: два пути обхода, с приоритетом ручной сессии.** ⚠️ Решение
  пересмотрено 2026-08-10: собственный Playwright (даже headed, даже с реальным
  Chrome) детектится Qrator-подобными защитами на уровне CDP-протокола автоматизации
  — сайт конкурента (foxford.ru) не проходим локальным браузером в принципе,
  Apify Cloud с прокси и UNBLOCKER-фолбэком тоже не прошёл (10/10 попыток
  заблокированы). Рабочая схема:
  1. Куки экспортируются вручную из обычного (не автоматизированного) Chrome
     пользователя, где сайт открывается нормально (`scripts/cookies_to_storage_state.py`
     конвертирует экспорт Cookie-Editor в Playwright `storage_state`). Если сессия
     сохранена — `app/pipeline.py` использует её с локальным Playwright.
  2. Если сохранённой сессии нет — обход идёт через **Apify Cloud** (актор
     `apify/website-content-crawler`) — внешний платный API, годится для сайтов
     без сильной защиты. Требуется `APIFY_API_TOKEN` в `.env`.
  Локальный Playwright с headed-прогоном без готовых кук (`scripts/capture_session.py`)
  практически бесполезен против CDP-детектящих защит — оставлен для слабо защищённых
  сайтов.
  ⚠️ **2026-09-16: библиотека обхода заменена с `playwright` на `patchright`**
  (drop-in замена, тот же API `patchright.async_api`) в `app/crawler/browser.py`,
  `app/crawler/crawl.py`, `app/pipeline.py`. Patchright исполняет служебные CDP-команды
  в изолированном контексте, а не в основном JS-контексте страницы — устраняет именно
  тот фингерпринт автоматизации, на котором палился обычный Playwright. **Не проверено
  на реальном foxford.ru** (нужна свежая сессия/капча, чтобы прогнать headed-режим) —
  до подтверждения ручной способ (куки + `storage_state`) остаётся основным путём,
  patchright пока даёт лишь дополнительный шанс, что и headed-прогон без готовых кук
  снова станет рабочим для защищённых сайтов.
- **Инкрементальный обход по дате из sitemap (2026-09-16).** Первый обход конкурента
  (и своего сайта) — полный: тянем все страницы из sitemap.xml, лимит
  `CRAWL_FULL_CRAWL_MAX_PAGES` (3000). Дальше — только страницы, у которых `<lastmod>`
  в карте сайта стал новее сохранённой даты (`Page.sitemap_lastmod`); остальные просто
  переносятся из прошлого снимка без похода на сайт. Раз в `CRAWL_FULL_RECHECK_DAYS`
  (30) обход снова делается полным — подстраховка на случай, если сайт не обновляет
  дату честно. Страница, пропавшая из sitemap (а он теперь читается целиком, без
  обрезки на первых 5 под-файлах), считается removed. Логика — `app/crawler/crawl.py`
  (`discover_sitemap_entries`, `plan_crawl`), `app/pipeline.py` (`_needs_full_crawl`).
  **Известное ограничение**: у обхода через Apify (фолбэк при блокировке) этой
  экономии нет — актор каждый раз обходит сайт заново целиком.
- Это инструмент для узкого круга людей — авторизация простая (Basic Auth), без
  регистрации/биллинга/мультитенантности.

Состояние на 2026-09-18: всё из первоначального плана сделано, проект в рабочем
режиме (пилот на реальных конкурентах). Ниже — что есть, и отдельно открытые хвосты.

- [x] Схема БД (PostgreSQL): `competitors`, `pages`, `page_snapshots`, `page_changes`
      (new/changed/removed + diff), `ai_analysis` (category, usp, cta), `notifications_log`,
      плюс `own_site_comparisons`, `schedule_config`, `page_fetch_cache`.
      Миграции Alembic — `migrations/versions/0001…0007`
- [x] Краулер (patchright, см. ограничения выше) со стелс-настройками; хранение и
      переиспользование `storage_state` на конкурента (`storage_states/competitor_<id>.json`)
- [x] Flow ручной сессии: экспорт кук из обычного Chrome →

- [x] Обработка блокировок: детект 403/challenge-страницы (`app/crawler/blocking.py`) →
      статус `needs_session` + алерт в Telegram, без бесконечных ретраев
- [x] Движок диффа по content-hash (`app/crawler/diff.py`): new/removed/changed по URL;
      перепроверка пропавших страниц обычным запросом (`app/crawler/recheck.py`) —
      404/редирект/жива
- [x] ИИ-анализ через Claude Code CLI headless (`app/ai/analyze.py`): JSON с
      category/usp/cta/summary, retry, параллельность `CLAUDE_CLI_CONCURRENCY`.

- [x] Дозаправка пропущенного ИИ-анализа (2026-09-18, `app/ai/backfill.py`): в конце
      каждого обхода добираем находки без разбора с прошлых прогонов (до
      `AI_BACKFILL_MAX_PER_RUN`), вручную — `scripts/backfill_ai_analysis.py`.
      Нужна потому, что инкрементальный обход сам пропуски не пересматривает
- [x] Планировщик APScheduler (`app/scheduler.py`), расписание редактируется в UI и
      хранится в БД. Единая точка запуска обходов — `app/crawl_manager.py` (защита от
      двойного запуска, общий лимит `CRAWL_CONCURRENCY`, остановка обхода). При

- [x] FastAPI-бэкенд: CRUD конкурентов, лента изменений, ручной триггер обхода одного/всех,

- [x] UI на Jinja2 в стиле CRM: дашборд, список конкурентов, карточка конкурента с вкладками,

- [x] Отчёты по каждому обходу — Google Docs/Drive (`app/integrations/google_docs.py`,

### Открытые хвосты

- **Прод — отдельный всегда включённый Мак, приложение НЕ в Docker (решено
  2026-09-21).** На macOS Claude Code хранит вход в подписку в Связке ключей, Linux-
  контейнер до неё не достаёт → `claude -p` в контейнере «Not logged in». Поэтому
  приложение запускается нативно под launchd (`scripts/run_prod.sh`,
  `scripts/install_launchd.sh`, `deploy/ru.ai-scout.app.plist`), Postgres — в Docker.
  Проверено на реальном Маке: из-под launchd `claude` авторизован (важно: нужна
  переменная `USER`, скрипт её выставляет). Управление — только Telegram-бот, без
  «обновить код через бота» (отклонено осознанно, чтобы не расширять поверхность
  атаки). Инструкция — README, раздел «Прод на отдельном Маке».
  `docker-compose.yml` оставлен для Linux-серверов, там не проверялся.
- **Google OAuth-приложение всё ещё в статусе Testing** → токен отзывается каждые
  7 дней. Перевести в Production (Google Auth Platform → Branding заполнить →
  Audience → Publish app) и перевыпустить токен — отложено до развёртывания на
  прод-Маке.
- **Apify-фолбэк не умеет инкрементальный обход** — каждый раз обходит сайт целиком.
- **Patchright не проверен на foxford.ru** (см. ограничения выше).
- Линтер (`ruff check`) даёт ~20 замечаний B008 в роутерах (стиль `Depends` в
  аргументах по умолчанию) — не баг, можно отключить правило в `pyproject.toml`.

## Технический стек

- Backend: Python 3.12+ / FastAPI
- Скрапинг: ручная сессия + локальный patchright (headless) как основной путь для
  защищённых сайтов; Apify Cloud (актор website-content-crawler) — фолбэк для сайтов
  без сильной защиты или когда сохранённой сессии нет
- БД: PostgreSQL
- Планировщик: APScheduler
- ИИ-анализ: Claude Code CLI headless (`claude -p`), подписка — без Anthropic API
- UI: Jinja2 (server-rendered), без отдельного SPA-фронтенда
- Уведомления и управление: Telegram Bot API, прямая интеграция в коде (без MCP/плагинов) —
  и исходящие уведомления, и интерактивное меню (aiogram, long polling)
- Деплой: отдельный Мак, launchd + Postgres в Docker (см. README); Docker Compose —
  только для Linux; Basic Auth

## Скиллы для этого проекта

Использовать проактивно при соответствующих задачах:

- **backend** — вся разработка FastAPI-эндпоинтов, роутов, слоя бизнес-логики,
  валидации запросов
- **database** — проектирование схемы Postgres, написание миграций и запросов
- **api-design** — именование и структура REST-эндпоинтов краулера/UI-бэкенда
- **testing** / **tdd** — при написании тестов для diff-движка и парсинга ИИ-ответов
- **diagnosing-bugs** — при отладке сложных багов краулера (антибот-детект, JS-рендеринг)
- **run** — запуск и проверка приложения (докер-компоуз, FastAPI dev-сервер) перед тем,
  как считать задачу выполненной
- **webapp-testing** — визуальная проверка UI (лента изменений, карточки) через Playwright
- **security-review** — перед деплоем: проверка Basic Auth, хранения `storage_state`/куки
  (чувствительные данные!), секретов (Telegram-токен и т.п.)
- **claude-api** — при работе с Claude Code CLI headless-режимом: параметры, стриминг,
  ограничения подписки vs API
- **setup-pre-commit** — по желанию, для линтеров/форматирования Python-кода

## Плагины / коннекторы (MCP)

На данный момент **не требуются**. Telegram-уведомления реализуются напрямую через
Telegram Bot API в коде проекта, а не через внешний коннектор — так надёжнее и не тянет
лишних зависимостей для внутреннего инструмента. Если в будущем понадобится интеграция
с внешними сервисами (например, выгрузка отчётов в Google Sheets), тогда подключить
соответствующий скилл (`google-sheets`) или коннектор через `connect-apps`.
